# SIGHT product engineering report

Status snapshot: 2026-11-12. This report separates current implementation from executed evidence. SIGHT is experimental assistive software; it is not a certified independent mobility aid.

## A. Product

The Android app combines spoken walking-route guidance with camera-based Explore, Find, and Read workflows. Users can submit a destination by voice or text, choose a numbered search result, start a provider walking route, and receive route progress from GPS while the app is foregrounded. They can explore the camera view, search supported object classes, read captured text, ask the OCR workflow to match words for a door, entrance, elevator, or bus stop, review recent visual observations, and explicitly save encrypted landmarks. They can opt into camera-relative traffic-object announcements during walking awareness or active route guidance. These capabilities are integrated in the Android application, but no completed real-world end-to-end walking study is claimed.

Voice commands are requested one at a time. On-device Android speech recognition is preferred; bundled offline English recognition is the fallback. SIGHT has no wake-word listener. Native tests decoded three clean synthetic command clips to expected intents on both API 30 and API 35 and returned no transcript for synthetic silence. API 35 synthesized 183,886 bytes of PCM using `en-us-x-tpf-local` (`networkRequired=false`). No physical microphone recognition or human confirmation that synthesized speech is audible has been evaluated.

## B. Navigation

Photon/komoot supplies place search. The default walking route comes from FOSSGIS OSRM's `routed-foot` service; an explicit preference can request additional mapped details from FOSSGIS Valhalla. Public routing is disabled until the user consents. Search and route coordinates are sent to those providers; camera images are not. Providers may log requests and do not provide a route accessibility guarantee.

The app supports numbered destination choices, route overview, foreground GPS guidance, pause/resume, repeat, distance to the next mapped maneuver, cancel, and recalculation after repeated accurate off-route fixes. Progress uses route geometry and screened GPS fixes. Stale, inaccurate, duplicate, or implausible fixes lead to uncertainty. Arrival requires a fresh nearby fix and user confirmation; the mapped point may not be the correct entrance. There is no lane positioning, sidewalk-position estimate, or indoor map matching.

Executed evidence: [three fixed public trips](../evaluation/results/product-navigation/summary.json) returned routes, all six selected searches had results, and the production engine replay covered six scenarios / 217 constructed fixes with zero automatic-arrival declarations, zero unsupported clearance claims, and zero failures. [API 35](../evaluation/results/product-android35/integrated-navigation-proof.json) and [API 30](../evaluation/results/product-android30/integrated-navigation-proof.json) instrumentation exercised the real Activity, CameraX, route parsing, consent, destination selection, and lifecycle with recorded HTTP responses, constructed GPS fixes, and recognized-transcript input. Both runs confirmed three live detector frames and that backgrounding stopped sensors. This was not physical GPS or microphone input and does not measure a person walking, accessibility, destination-search quality, or field location performance. Routes can contain unsuitable paths, steps, or crossings.

## C. Road awareness

The app contains a bounded, asynchronous direct LiteRT reader for Intel's `road-segmentation-adas-0001` model, separate from the MediaPipe COCO object detector. The four model outputs are background, road, curb, and marking. A user can request the road diagnostic and inspect regions/timing in Developer. Automatic road-surface speech is disabled. The model's curb label has no independent SIGHT accuracy claim; markings are not crosswalk recognition. It does not output sidewalks, crossing signals, vehicle motion, physical hazards, clearance, or permission to cross. The current feature contract keeps surface speech disabled.

Automatic road voice is **disabled** after the balanced sealed 40-image held-out presence evaluation failed one gate. At the frozen calibration operating point (component coverage at least 0.02; mean posterior at least 0.75), held-out counts were 17 TP, 1 FP, 3 FN, and 19 TN. Precision was 0.9444 and recall 0.8500, but false events/image was 0.025, exceeding the maximum 0.02. The same held-out set had strict road-pixel IoU 0.6448. Calibration selected that operating point on a separate 30-image split: 11 TP, 0 FP, 4 FN, and 15 TN. Selection, calibration, and held-out splits each have 30, 30, and 40 images; no parameters were tuned on the final split. See the [balanced evaluation report](../evaluation/results/pedestrian-balanced/report.md), [frozen protocol](../evaluation/results/pedestrian-balanced/protocol.json), [selection](../evaluation/results/pedestrian-balanced/selection.json), [calibration](../evaluation/results/pedestrian-balanced/calibration.json), and [held-out results](../evaluation/results/pedestrian-balanced/held-out.json). The older [initial general-photo probe](../evaluation/results/pedestrian/calibration.json) is a distinct failed experiment, not the final road result. The corrected LiteRT model also passed fixed-photo Android pipeline checks on API 30 and API 35; these confirm inference wiring, not additional road accuracy beyond the sealed dataset. See [API 35 road proof](../evaluation/results/product-android35/native-road-pipeline-proof.json), [API 30 road proof](../evaluation/results/product-android30/native-road-pipeline-proof.json), and the [product-validation summary](../evaluation/results/product-validation/summary.json).

The object-based awareness engine is separate from the road model. During explicit “walking awareness” or active route guidance, it can announce one of the largest currently visible eligible COCO tracks per observation among car, truck, bus, motorcycle, bicycle, person, traffic light, bench, and fire hydrant. Admission requires two consecutive observations, per-observation and aggregate confidence at least 0.70, box area at least 0.02, and current/last-seen evidence no older than 1.5 seconds. The spoken direction is left/center/right in the camera image. A traffic-light message explicitly says signal state is unknown; every object announcement says movement is unverified. A category/image-direction pair has a 20-second cooldown. No motion, approach, crossing, or event-recall claim is made. A deterministic safety layer checks announcement freshness, grounding, and support at dispatch/start/continuation, blocks unsafe crossing/clearance/avoidance language and visual metric-distance claims, and invalidates navigation cues when the route speech revision changes or its deadline expires.

## D. Object finding

The deployed object detectors cover 80 COCO categories, with Fast Lite0 and selective Inspect Lite2. Find uses fresh camera evidence and temporal confirmation; uncertain or unsupported categories can be declined. Position descriptions use the camera image, not the user's body or walking direction. Camera orientation can separately report a recent rear-camera pitch and, when sensor confidence permits, magnetic heading; it cannot infer body heading or walking direction. There is no color classifier, identity verification, metric depth, door/entrance object detector, stair detector, or validated free-space analysis.

The product also supports a bounded OCR text search for selected terms: door/entrance/exit, elevator/lift, and bus-stop/stop-number wording. It analyzes recognized words from a fresh captured frame using ML Kit; it can quote matching sign text, but it does not confirm that the physical feature exists, identify the sign/object, or establish its location.

Historical SIGHT 3 held-out evaluation on 80 credited photographs reported Lite2 AP50 0.6040, AP50:95 0.4158, operating precision 0.9491, recall 0.3394, and 11 false positives. This is a fixed subset detector benchmark. It is not a new product-validation result or an estimate of real task success. Recall for backpacks (0/10), handbags (0/9), bottles (0/12), and books (0/24) was zero in that held-out slice. See the [original detector report](../evaluation/results/v3-detection/report.md) and [SIGHT 3 report](engineering-report-v3.md).

## F. Accessibility

Compose provides labelled actions, headings and status feedback, scalable text, large touch targets, a two-row large-font navigation layout, typed alternatives, and user-initiated voice controls. Volume Up starts one command and Volume Down stops assistance while the app is open; these keys replace normal volume adjustment during that time. There is no always-listening mode.

API 30 and API 35 instrumentation suites passed 15 checks each, including UI semantics/scaling/lifecycle and integrated navigation. Automated tests do not establish human TalkBack focus order or task success. There has been no human TalkBack usability evaluation, blind-participant study, or physical-device accessible task-completion study. Implementation features are not an accessibility certification.

## G. Meta glasses

The optional Meta Wearables Mock Device Kit adapter is a separate mock APK/project. It imports shared production core and object-perception code. The current official mock suite passed all 8 native instrumentation checks in 8.262 s, including decoded frame conversion and a real detector/Find path. This is not the phone app controlling real glasses. It does not establish physical camera calibration, optics, head orientation, synchronized capture timing, microphone input, speaker routing, comfort, or battery life. No real glasses hardware has been tested. See [Meta integration limits](meta-v3.md).

## K. Remaining blockers

- Automatic road voice remains disabled because the held-out presence gate failed. A stronger, independently evaluated road model and a passing release gate are needed before activation.
- Dedicated sidewalk, crosswalk, pedestrian-signal-state and depth-based obstacle assessment remain unavailable or unvalidated. They need suitable mobile models and independent evaluation; mapped tags, image-relative detections and OCR word matching cannot supply those guarantees.
- Physical Android performance, sustained runtime, battery, real microphone behavior, human TalkBack and blind-participant usability, outdoor route quality, and actual glasses behavior remain unverified.
